Why This Project?

Chapters 01–03 were all about data — saving it, transforming it, displaying it. Chapter 04 is about presentation. How do you take static content and make it feel alive? How does scroll position drive the page experience? How do you build a layout that works at every screen size?

The portfolio is the most universally useful project in this curriculum. Every developer needs one. Building it from scratch — with animations you actually understand — is more valuable than downloading a template you can’t explain.

CSS Keyframe Animations

The hero section loads with staggered @keyframes fadeUp animations triggered purely by CSS — no JavaScript needed for the initial reveal.

Intersection Observer API

A JavaScript API that watches when elements enter the viewport. When they do, a visible class is added — triggering CSS transitions that reveal content as you scroll.

CSS Transitions vs. Animations

Transitions respond to state changes (like adding a class). Animations run on a timeline. Knowing when to use each is a key layout design skill.

Multi-Section Layout

A sticky nav, full-height hero, alternating grid sections, and a contact form — all in one file, all responsive, all vanilla CSS grid and flexbox.

The AI Angle for This Chapter

Design-heavy chapters are where AI shines most — and where your judgment matters most. AI can generate beautiful CSS instantly. But it can’t decide what you want to say, how you want to be perceived, or which projects represent your best work.

Your portfolio content is the constraint AI can’t solve for you. Before prompting any CSS or layout, write the copy: your headline, your one-sentence about, your three best projects. AI builds around your content. Content without a frame is just noise.

“Design is what you intend. Animation is how you reveal the intention.”

Questions to answer before prompting layout:

  • What’s the one sentence someone should remember about you after leaving this page?
  • What are the three projects you’d most want a collaborator or client to see?
  • What do you want the page to feel like — minimal and sharp, or rich and textured?
  • What’s the one action you want visitors to take? (Contact? View GitHub? Watch the show?)

Before You Build — Plan the Sections

  1. List the sections your portfolio needs in order. What’s the first thing someone sees? What’s the last?
  2. For each section, describe the animation: does it fade up from below, slide in from the side, or load immediately?
  3. What’s the difference between an animation that fires once (on load) and one that fires every time the element enters the viewport? When would you want each?
  4. How does a sticky nav change when you scroll past the hero? Describe what should change visually.
  5. What should happen when the contact form is submitted? There’s no backend — so what’s the honest user experience?

A portfolio with clear answers to these five questions will feel intentional. One without them will feel like a template someone filled in.

Build It

Phase 1

Scaffold the sticky nav and hero

Start with structure before animation. Get the nav fixed at the top and the hero section filling the full viewport height. Content and copy first — animation layer comes later.

Build a single-page portfolio in vanilla HTML/CSS/JS.
Color palette: #111 background, #e00 red accents, #f5f5f5 text.
Sticky nav with brand name on the left, nav links on the right.
Full-height hero section (min-height: 100vh) with an eyebrow
line, a large headline, a subheading, and two CTA buttons.
No animations yet. Focus on layout and copy placement.
Phase 2

Add CSS keyframe animations to the hero

The hero loads immediately — no scroll trigger. Use @keyframes with staggered animation-delay values so the eyebrow, headline, subheading, and buttons each appear 0.2s apart. This creates a "reveal" feel without JavaScript.

Add a fadeUp @keyframes animation that moves elements from
opacity:0 translateY(24px) to opacity:1 translateY(0).
Apply it to each hero element with staggered delays:
eyebrow: 0.2s, headline: 0.4s, subheading: 0.6s, buttons: 0.8s.
Use animation-fill-mode: forwards so elements stay visible
after the animation completes. Start each at opacity:0.
Phase 3

Build the content sections + scroll reveal classes

Add the About, Skills, Projects, and Contact sections. Apply a .reveal class to every element that should animate on scroll. Style .reveal as hidden (opacity:0, translateY) and .reveal.visible as fully shown. The JavaScript that adds visible comes next.

Add four content sections: About (two-column with bio and stats),
Skills (grid of skill cards), Projects (card grid with links),
Contact (split layout with info on left, form on right).
Give every element that should animate the class "reveal".
Style .reveal as { opacity:0; transform: translateY(32px);
transition: opacity 0.65s ease, transform 0.65s ease; }
and .reveal.visible as { opacity:1; transform: translateY(0); }
Phase 4

Wire up Intersection Observer

This is the JavaScript layer that watches each .reveal element and adds the visible class when it enters the viewport. The CSS does the animation — JavaScript just toggles the class.

Write a JavaScript Intersection Observer that:
1. Selects all elements with class "reveal"
2. Creates an IntersectionObserver with threshold: 0.12
3. In the callback, if entry.isIntersecting is true,
   adds the class "visible" to the element
The observer should fire once per element — elements don't
need to hide again when scrolled past.
Phase 5

Polish: skill bars, form UX, and mobile

Three final details that separate a finished portfolio from a draft: animated skill bar fills (triggered by the same observer), a contact form that gives honest feedback (no backend — just a confirmation message), and a responsive layout that looks right on mobile.

1. Skill bars: each .skill-bar has a data-width attribute.
   When its parent .reveal becomes visible, set
   bar.style.width = bar.dataset.width + '%' with a 200ms delay.
2. Contact form: on submit, prevent default, show a loading
   state on the button, then after 900ms show a success message
   and reset the form. No actual email sending.
3. Mobile: test at 375px. Nav links should collapse or wrap.
   Two-column grids should drop to one column.
   Hero text should scale with clamp().

Concepts You Just Used

  • @keyframes — define a reusable animation timeline in CSS
  • animation-delay — stagger animations so elements appear one after another
  • animation-fill-mode: forwards — keep an element in its final animated state
  • transition: opacity transform — smoothly animate between two CSS states
  • IntersectionObserver — watch when elements enter/exit the viewport without scroll event listeners
  • entry.isIntersecting — boolean that tells you if the element is currently visible
  • element.classList.add('visible') — the bridge between JS observation and CSS animation
  • clamp(min, preferred, max) — fluid typography that scales between a minimum and maximum size
  • position: sticky — an element that scrolls normally until it hits a threshold, then sticks
  • scroll-behavior: smooth — enables smooth scrolling for anchor links

Intersection Observer replaced scroll event listeners for most animation use cases. Scroll listeners fire hundreds of times per second and can tank performance. IntersectionObserver fires only when the visibility state actually changes — it’s purpose-built for exactly this pattern.

Reflect

  1. What’s the difference between a CSS transition and a CSS animation? Give an example of when you’d use each.
  2. Why is IntersectionObserver better than a scroll event listener for this use case? What would break if you used a scroll listener instead?
  3. The hero animations use CSS only. The scroll animations use JavaScript. Why the difference? Could you do both with just CSS?
  4. The contact form doesn’t actually send anything. What would you need to add to make it functional — and what’s the simplest way to do that without a backend?
  5. If a recruiter or client landed on your portfolio, what’s the one thing you wish it said more clearly? How would you change it?

The skills you used in this chapter — layout, animation, observer APIs — appear in every modern web app. You’ve now built the full stack of browser capabilities: storage, DOM, math, rendering, and motion.
